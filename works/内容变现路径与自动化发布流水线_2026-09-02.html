4你的洞察是对的：克制排版 = 降低认知负载，它直接换算成流量

「很直接没啥花里胡哨、人味更高、可信度更高」——这个判断有认知心理学支撑，且有可量化的参数。

4.1 为什么花哨排版会赶走读者

2026 年的流量环境下，用户注意力已从「获取信息」退化为「过滤信息」。装饰性元素（边框、渐变、花哨分割线、动图贴纸）属于非语义信息，会挤占读者处理核心观点的带宽——结果是文章看起来很美，读完大脑一片空白，甚至视觉疲劳直接跳出。

装饰性排版（业余）

目标：视觉愉悦 / 自我表达
重心：找精美模板
视觉逻辑：元素堆砌
结果：点赞数好看，完读率崩

转化型交付（专业）

目标：降低认知负载 / 驱动 CTA
重心：设计信息流向
视觉逻辑：视觉引导线
结果：完读率高 → 搜一搜收录稳 → 长尾流量

关键因果链：排版杂乱 → 完读率低 / 停留时长短 → 被平台判定为「低质内容」→ 搜一搜收录不稳定 → 长尾流量归零。排版不是审美，是流量工具。

对现有工具的影响：render_wechat.js 不是推倒重来，是降级

行途蓝 #056DE8 作为唯一强调色完全 OK，品牌识别度就靠它。要动的是：砍掉装饰性元素（背景、花哨分割线、多色），统一字号行距段距，把「设计感」的预算从正文转移到封面图和头图上——正文老实系统默认，封面图做足品牌感，这才是高级感的正确投放位置。

⚠️ 2026-09-02 修正：主线建议已变更，动手前先看这条

上面「主 Playwright」的建议，在后续调研中发现两个此前未纳入的硬约束，优先级高于原建议：

① 封号风险。浏览器自动化模拟登录公众号后台，行业资料明确标注违反《微信软件许可及服务协议》「自动化操作」条款，有封号与司法风险；适用场景被限定为「个人订阅号、低频自用、只存草稿后人工确认」，明确不适合高频/商用/多账号。而公众号是你 IP 战略的主阵地、职业安全垫的载体——用安全垫载体去冒封号风险，是目的与手段倒置。

② API 权限口径冲突。行途技术手记为未认证个人订阅号。官方接口文档「适用范围」表把 draft/add 对订阅号标为可调，但微信开放社区有大量实测反馈：未认证/个人订阅号调用返回 48001 api unauthorized。官方回答原文亦称「该接口仅对企业主体且已完成微信认证的公众号开放」。同时 freepublish 发布接口自 2025-07 起已对个人主体回收。

修正后的执行顺序：先实调一次 draft/add 定生死（一个 curl，成本极低）。 · 返回 media_id → 改走 API 路线为主（比 Playwright 稳定得多：不受 UI 改版影响、不需反检测、不需关沙箱；且「只到草稿箱、人工终审」本来就是我们的设计原则，与个人号权限天然契合）。 · 返回 48001 → Playwright 成为唯一路线，此时必须重新评估封号风险后再决定是否推进。

补充坑位：AppSecret 自 2025 年底起已迁至微信开发者平台（developers.weixin.qq.com/platform，不在 mp 后台），仅在「启用/重置」时显示一次，关窗即焚；IP 白名单必配，否则报 40164。 详见 outputs/工作流编排工具选型判断_2026-09-02.html（含完整 curl 测试命令）。

def push_draft(md_path, collection, cover):
    html = render_wechat(md_path)          # 复用已有 render_wechat.js
    ctx  = browser.new_context(storage_state="state/wechat-state.json")
    page = ctx.new_page()
    goto_draft_editor(page)
    fill_title(page, frontmatter.title)    # 前 13 字含核心词（SEO）
    fill_author(page, "行途")
    fill_content(page, html)               # section+span 渲染，规避样式过滤
    upload_cover(page, cover)              # 900×383
    select_collection(page, collection)    # ← 你要的「合集/系列」在这里定义
    fill_summary(page, frontmatter.digest)
    save_draft(page)                       # ⚠️ 只存草稿，绝不点发布
    return draft_url                       # 返回链接，人工审核后手动发布

四条红线（写进脚本，不可绕过）

① 只到草稿箱——脚本里绝不出现「点击发布」的动作，发布按钮 100% 人工点击；
② 登录态绝不入库——state/ 目录写进 .gitignore，且绝不上传到任何公开仓库；
③ 频率控制——批量操作加随机间隔，避免触发微信风控；
④ 每步截图存档——失败时可回溯，这也是排查微信编辑器样式过滤的唯一手段。

两个已知技术坑（提前规避）

① 微信编辑器会过滤样式：成熟方案的做法是用 section + span 渲染模式替代 div + class，兼容性显著更好——这也是 render_wechat.js 需要同步改造的点；
② 沙箱内浏览器会闪退：你的环境坑记录里已有结论，跑浏览器自动化时必须关闭沙箱，否则 Chromium 子进程被 SIGKILL 且零报错输出。

6待拍板：5 个决策点

我给了推荐项，你可以直接采纳或改——改完我就照着落地。

D1 · 内容形态优先级影响全局
A. 长文为绝对主力 + 开源项目为背书（推荐）公众号长文是主阵地，tokenhub_bench 等开源项目同步推进，视频号等长文跑通后再开。不变现也积累作品集。
B. 长文 + 同步启动视频需要额外投入拍摄/剪辑时间。风险：在职低调约束下时间本就稀缺，同时开两个坑大概率两个都做不深。
C. 加入抖音漫画图文分成系数 1x，无作品集价值，与你的核心资产错配。
D2 · 排版风格影响工具改造
A. render_wechat.js 降级为「克制排版」（推荐）保留行途蓝作唯一强调色，砍掉装饰元素，统一 15-16px / 1.75 行距 / #333333 / 段距 8-15px。改造量小，收益是完读率和搜一搜收录。
B. 保持现有行途蓝风格品牌识别度高，但需先验证当前风格是否含装饰性元素、是否拖累完读率。
D3 · 自动化范围影响投入节奏
A. 先跑 P0 草稿自动化，验证后再推 P1-P3（推荐）一周内能看到「脚本填好草稿、你点一下发布」的真实效果，再决定投多少。
B. 一次设计四期全部再动手架构更完整，但反馈周期长，容易在设计上过度投入而迟迟不发布。
D4 · 合集 / 系列怎么定影响涨粉引擎
A. 沿用已规划的「省 Token 专题」三线结构（推荐）A 线六层落地 + B 线工具横评 + C 线模型选型，共 16 篇，天然就是合集。再单开「技术闪记」「行途故事」两个长期合集。
B. 重新设计合集体系如果你觉得现有规划需要调整，我先出合集设计再落地。
D5 · 存量内容怎么消化直击痛点
A. 按「可直接发 / 需改写 / 废弃」三分类，先清可直接发的（推荐）你本地躺着 182 个 outputs 文件、1125 条素材。先盘一遍，把能直接发的排进发布日历，这是最快的正反馈。
B. 全部重新写质量更高，但存量继续贬值。
